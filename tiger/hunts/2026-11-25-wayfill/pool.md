## P01 - Review a guide by walking it: machine quote check, review mode, text lock

`deepen` `effort M` round 1 - anchors 8/8 - peers 8/10 (n=2)

- **Outcome:** A Czech-reading person can check a draft guide in one sitting inside the product: each step beside the real form, every official quote already confirmed word for word by machine, the open review notes shown as questions. They hand over an attestation that a maintainer commits, so production shows 'Checked guide' on a real form for the first time. Afterwards, any edit to a reviewed guide's text fails check-guides mechanically.
- **Builds on:** The review law and the guide door (parseGuide, check-guides, drift, reader-only refresh), plus the sentence door findSentence that gist and askPage already use.
- **Mechanism:** Three parts. (1) A script, npm run guide:review -- <id>: fetch instructionsUrl and each official.url with the fetch the guide scripts already have (a PDF already comes back as page blocks), run every official.text through findSentence, print 'found word for word' or 'not found' per step, and run drift for that guide. (2) Review mode in Wayfill when the matched guide is a draft and drafts are on: each step shows English and Ukrainian together beside the real form, its quote-check result and the reviewNotes that name it, with 'Agrees with the instructions' or 'Needs a change' plus a note. The finish card exports an attestation: guide id, sha-256 of the checked text, the name and languages the reviewer types, the date. The app never writes the guide; the reviewer, or a maintainer quoting the attestation, makes the commit, as guides/README.md already allows. (3) The review commit stores that digest in a new optional key reviewedText. It covers steps, notes, quotes, field ids and kinds, not labels, so the reader-only refresh exception still holds. parseGuide and check-guides recompute it and refuse a reviewed guide whose text changed.
- **Evidence:** Observed: the dossier records check-guides printing 0 reviewed, and shippable() leaves drafts out of every build people use, so no real form gets a library guide although README.md:24 promises checked steps. Observed: a review today is four comparisons done by hand over JSON (guides/README.md:64-70); the word-for-word one is mechanical and findSentence already does it for gist and askPage. Observed: check-guides ties fingerprints to match.fields, but nothing ties a review to the step text, so 'editing a reviewed guide's text returns it to draft' holds by convention only. Observed: the three drafts carry 19 quotes per language and 25 open review notes. Hypothesis: a Czech reader finishes cz/oznameni-zmen (10 steps, 3 quotes, 8 notes) in under 30 minutes this way. Prior art: A2J Author guided interviews, written and checked by legal aid staff, used over 7 million times by CALI's own count (https://www.cali.org/content/a2j-author).
- **Risk:** Ticking through becomes rubber-stamping. Mitigation: the attestation cannot be exported while a quote check failed, a review note is unresolved or a step was never opened; the name is typed by the person and no code path fills reviewer or reviewedOn. A source page that needs scripts cannot be read by happy-dom: report 'could not be read' and leave that quote to the person, never count it as found. Part 1 (the script) is S and can land alone.
- **Verify:** check-guides prints at least '1 reviewed' (today: 0 reviewed, 3 draft, 1 demo). A build without VITE_GUIDE_DRAFTS that opens Oznameni-zmen.pdf shows data-testid guide-chip with data-kind reviewed. Changing one word of a reviewed step makes check-guides exit 1, while guide:new --refresh on the same form still passes. guide:review prints a verdict for all 19 quotes of the three drafts. The minutes one reviewer needs for cz/oznameni-zmen are recorded.
- **Why it matters:** It turns the product's central promise, steps a named person checked, from zero instances into a repeatable hour of work per form, and makes the review law enforceable by the gate instead of by convention.

## P02 - Ground model-built steps in the form's own printed instructions

`connect` `effort M` round 1 - anchors 8/8 - peers 4/10 (n=2)

- **Outcome:** On a form with no library guide, a step shows the sentence of the form's own instructions it rests on, in the form's language, found word for word in the document the person opened, with Show me pointing at it. WizardStep gains the optional source. Wayfill shows it in the existing quote figure, captioned 'This form's own words', with Show me calling host.locate({blockId}). The chip stays the AI chip, never 'Checked'. The same call can seed guide:new skeletons with quote-verified drafts for the 18 corridor forms without a guide.
- **Evidence:** Observed: prompts.buildWizard sends fields only, while readPdf already builds the document's blocks and boxes and PdfHost.locate already outlines a block. Observed: the same door pattern ships in this repo for gist and askPage. Hypothesis: explanations move closer to what the instructions say; this is not measured.
- **Risk:** A verbatim sentence proves presence, not that it supports the explanation. Mitigation: caption it as the form's own words, keep the AI chip, never call it checked. On-device context is small: use budgeted block selection and measure against the session's input quota before turning it on for the device. It renders per field: the field's date shape through the existing writers, a country as the matching option or as its name in the form's language via Intl.DisplayNames, a name as typed. - **Evidence:** Observed: the profile is keyed by fieldId (a print-only PDF's key is 'p1-x293-y630') and handed to the on-device model as raw JSON, so a saved answer can reach another form's field only by a model guessing. Observed: Suggest shows only when the local model is 'available', a state the dossier records as not yet observed on real hardware. Observed: carryOver already does a model-free join by label, but only within one site and one tab session. Prior art: Chromium autofill stores server and local-heuristic field-type predictions per field (https://chromium.googlesource.com/chromium/src/+/main/components/autofill/core/browser/autofill_field.h); the autofill token vocabulary is standard (https://developer.mozilla.org/en-US/docs/Web/HTML/Attributes/autocomplete). Hypothesis: the 21 corridor forms share most of about 15 personal facts; this is not counted yet.
- **Risk:** A wrong concept on a legal form, above all another person's block (spouse, child, employer, representative). Mitigation: a field under a section naming another party gets no concept unless a reviewed guide gives one; every prefilled answer is marked and must be confirmed with Next; model-given concepts are labelled as the AI's match. The contract change is one optional field, exported to the JSON Schema for Android. The whole is L; guides plus autocomplete plus five concept families is M.

- **Why it matters:** It splits the work the way the hybrid design intends: the model only labels structure, the device joins the values. The product's most personal feature stops depending on a local model that few devices have, and Wayfill becomes a private set of papers that fills each next office's form.

## P05 - Account for every field: live values at each step, a re-read finish

`deepen` `effort S` round 1 - anchors 8/8 - peers 9/10 (n=2)

- **Outcome:** The wizard always shows what the form holds now, never blanks a field it did not change, and shows an agent's accepted answer in its step. It ends with an account of every field, re-read from the page: confirmed, changed since, required and empty, or in error.
- **Builds on:** Proof of each write (a write counts only when read back), and the fingerprint binding of Handrail proposals.
- **Mechanism:** (1) On entering a step, read the page's values for that step's fields and reconcile: a value the page holds that the wizard did not write is shown as 'already on the form' and becomes the step's answer. (2) Next writes only fields whose answer differs from what the page holds, so an untouched optional field is never cleared. (3) At build, every field no step covers gets a basic step marked 'No AI used', and the toolbar counts them ('the AI covered 12 of 19 fields'); this applies the door's 'dropped and counted' rule to wizards. (4) The finish card calls readValues and readErrors once more and lists per field: holds your answer, changed since you answered, required and still empty, or the form shows an error, each with a jump to the step. 'N fields were filled in' is said only for what the re-read confirms. (5) An accepted Handrail proposal lands in the same state.
- **Evidence:** Observed: Wayfill calls host.readValues exactly once, when the guide is built. commit() then sends every field of the step, including an empty string, and fill.ts clears a text field on an empty string. So a value that arrived after the build is invisible in the step and is erased by Next when the field is optional. Such a value can be typed in the original pane (which opens beside the wizard by default), set by a page script, or accepted from the agent (HandrailPanel writes straight to the page and tells Wayfill nothing). Observed: the finish card reports filled.length from memory, not from the page. Observed: parseWizard gives optional fields the model skipped no step and returns no count. The validation protocol fails the whole corridor on a single false 'filled' claim. All of this is read from the code; none of it was run.
- **Risk:** A re-read on every step costs a message round trip in the extension and can race a page that is still validating: read once on step entry and reuse the read after the write that already happens. Reconciling could surprise a person who cleared a field on purpose: show 'already on the form' with the value and let them empty it explicitly.

- **Why it matters:** It extends the proof from each single write to the whole form at the moment the person is about to send it, which is exactly the claim the validation protocol's pass or fail rests on.
